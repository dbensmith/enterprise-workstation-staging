A group folder may hold the token `{Platform}`; the validator expands it with the platformId of each model that has files in that group. Validator input is `records = every models[].files entry plus every shared entry`.

Finding object (every Test-* function in this plan returns these): `[pscustomobject]@{ PSTypeName = 'Kit.FirmwareFinding'; Status = 'Pass'|'Warn'|'Fail'; Check = 'Manifest'|'Volume'|'Names'|'Files'|'Hash'|'Duplicate'|'Folders'|'Root'|'Password'|'Ready'|'Layout'|'Notes'; Message = <short reason>; Path = <manifest path or ''>; Group = <group id or ''> }`.

Layout file (data only, read by Get-KitFirmwareLayout; the committed fixture below is the exact file Task 3 creates and Plans 02-02, 02-03 and 02-05 reuse):
```powershell
@{
    SchemaVersion = 1
    VolumeLabel   = 'FX_TOOLS'
    FileSystem    = 'FAT32'
    Captures      = @(
        @{ Name = 'fx-diag'; PackageId = 'fxdiag1'; Version = '1.0'; Snapshot = 'fx-diag.snapshot.psd1' }
    )
    Groups        = @(
        @{ Id = 'G-New'; Folder = 'Vendor\BIOS\New'; Source = 'BiosImage'; Closed = $true; Default = $true
            Verified = @{ Status = $false; Model = @(); Bios = ''; Date = ''; By = '' } }
        @{ Id = 'G-Current'; Folder = 'Vendor\BIOS\Current'; Source = 'BiosImage'; Closed = $true; Default = $true
            Verified = @{ Status = $false; Model = @(); Bios = ''; Date = ''; By = '' } }
        @{ Id = 'G-Diag'; Folder = 'EFI\FX'; Source = 'Captured:fx-diag'; Closed = $false; Default = $true
            Verified = @{ Status = $false; Model = @(); Bios = ''; Date = ''; By = '' } }
        @{ Id = 'G-Win'; Folder = 'firmware\fx\{Platform}'; Source = 'WindowsFlashTool'; Closed = $true; Default = $true
            Verified = @{ Status = $false; Model = @(); Bios = ''; Date = ''; By = '' } }
        @{ Id = 'G-Dev'; Folder = 'FX\DEVFW'; Source = 'FlashImage'; Closed = $true; Default = $false
            Verified = @{ Status = $false; Model = @(); Bios = ''; Date = ''; By = '' } }
    )
}
```
Layout rules: top-level keys exactly SchemaVersion, VolumeLabel, FileSystem, Groups plus optional Captures; group keys exactly Id, Folder, Source, Closed, Default, Verified; Verified keys exactly Status, Model, Bios, Date, By. Source is BiosImage, FlashImage, WindowsFlashTool or `Captured:<capture name>` naming an entry of Captures. A Verified block with Status $true must carry a non-empty Model array, Bios, By and a Date of the form yyyy-MM-dd.

Object Get-KitFirmwareLayout returns: `PSTypeName Kit.FirmwareLayout; Path; SchemaVersion; VolumeLabel; FileSystem; Groups = @([pscustomobject]@{ Id; Folder; Source; SourceKind ('BiosImage'|'FlashImage'|'WindowsFlashTool'|'Captured'); CaptureName ('' unless Captured); Closed; Default; Verified = [pscustomobject]@{ Status; Model; Bios; Date; By } }); Captures = @([pscustomobject]@{ Name; PackageId; Version; Snapshot; SnapshotPath })` where SnapshotPath is Snapshot joined to the layout file's folder (the file need not exist).

Private seam (mocked by every later plan with `Mock Get-KitVolumeInfo -ModuleName Kit.Core`): `Get-KitVolumeInfo -Path` returns `[pscustomobject]@{ Root = 'E:\'; FileSystem = 'FAT32'; Label = 'HP_TOOLS'; IsRemovable = $true }`, or $null when the path has no drive letter (UNC) or the drive is not ready. It uses `[System.IO.DriveInfo]` (no CIM, no admin).
Private helpers: `Get-KitStagePathProblem -RelativePath <string> [-Size <long>]` returns [string[]] of reasons (empty array when the path is fine). `Get-KitClosedFolder -Manifest <object>` returns [string[]] of the concrete relative folders of every group with closed true: the group folder, with `{Platform}` replaced by the platformId of each model that has files in that group (an object built in memory works as well as one read from JSON, because only property access is used). Plan 02-03 reuses it for -RemoveStale, so keep it a separate function with that exact name and parameter.

Test helper that Tasks 1 and 2 define inside tests/Firmware.Check.Tests.ps1 BeforeAll (independent of any writer, so this plan has no dependency on Plan 02-03): `New-TestStick -Root <path> -Record <hashtable[]> [-Group <hashtable[]>] [-Model <hashtable[]>]` writes each record's bytes (run-time `[byte[]]`) to Root\<path>, computes sha256 (lower case) and optional vendor hash with Get-FileHash, builds the manifest object above with `[ordered]`, writes it with `[IO.File]::WriteAllText($path, $json, [Text.UTF8Encoding]::new($false))` using ConvertTo-Json -Depth 6, and returns the manifest path. It also writes the READY marker (the lower-case SHA-256 of the manifest file, then a line break, ASCII) unless `-NoReady` is given, so a hand-built stick is a complete stick and a test that wants an unmarked one asks for it. A test that edits the manifest text after New-TestStick must either rewrite READY or call Test-FirmwareStage with -IgnoreReadyMarker.

- Label mismatch is a Fail in the validator because the vendor's pre-Windows diagnostics only run from a volume named as the layout says (02-RESEARCH.md Layout Evidence, HP FTP release notes).
